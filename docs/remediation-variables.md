# Remediation variables

Scope: every topic toggle and rule toggle of the collection. Audience: operators and
reviewers. Jira: FREES-55, FREES-53 (full catalogue).

This page is generated by `make toggles` from the rule catalogue
[`roles/remediate/vars/rules.yml`](../roles/remediate/vars/rules.yml), together with the
topic toggle defaults in `defaults/main.yml` and their argument specifications in
`meta/argument_specs.yml` of both the `remediate` and the `audit` role. Do not edit any of
them by hand: `make lint` fails when one differs from the catalogue. The catalogue itself is
generated from the pinned content ([control families](control-families.md)).

The toggles are flat booleans ([ADR 0011](adr/0011-control-toggles-and-cleanup.md)). A
family toggle defaults to `true`, and a rule toggle that is not set follows its family
toggle, so setting `linux_compliance_<family>_enabled: false` once switches off every
catalogued rule of the topic, and a rule toggle set explicitly wins over its family
toggle. The remediate role cleans up a switched-off rule that it applied before, and the
audit role excludes it from the scan and reports it as `disabled`, naming the controlling
variable. How the toggles combine with the global opt-in and the disruptive allow-list is
described in [the remediation guide](remediation.md#effective-state-of-a-rule). Pass
them as JSON on the command line, for example `-e '{"linux_compliance_auditd_enabled":
false}'`.

## What the catalogue covers

The catalogue holds every rule that a profile of the pinned content selects, whether or
not the collection can remediate it yet, so every rule of those profiles has a rule toggle
and belongs to one topic. A rule with the strategy `audit_only` has no native remediation
yet: the audit honours its toggles, and remediation reports it as `not_implemented` and
changes nothing for it.

When a topic toggle is `false` but no catalogued rule of its family is selected by the
profile, for example `linux_compliance_auditd_enabled` with the Ubuntu 24.04
`cis_level1_server` profile, which selects no auditd rule, both roles print a runtime
warning that starts with `WARNING:` and says that the toggle excludes nothing. When both
roles run in the same play, the warning is printed once by each role. Rules of content
outside the catalogue, such as user-supplied content, have no toggle; disable them with
`linux_compliance_audit_disabled_rules`.

## Umbrellas

Families that belong together are grouped by an umbrella toggle, for example
`linux_compliance_services_enabled` for `sssd`, `time_sync`, `mail` and the other service
families. An umbrella is either a name of its own, such as `services`, or a family that
heads it, such as `pam` for `pwquality`, `pwhistory` and `faillock`. There is one level.
Precedence, from the most specific toggle:

1. A rule toggle that is set wins, in both directions, as before the split.
2. Otherwise the rule is on only when both its umbrella toggle and its family toggle are
   on. An umbrella toggle that is `false` switches off every family it groups, and a family
   toggle that is `true`, such as its default, cannot switch one back on: a family toggle
   only narrows its umbrella.

Every umbrella keeps the name of the family that it was split from (FREES-53), so
`linux_compliance_services_enabled: false`, `linux_compliance_pam_enabled: false` or
`linux_compliance_firewall_enabled: false` still switch off every rule that the family
held before the split, and an allow-list entry that names an umbrella still allows every
disruptive family it groups. No toggle was renamed or dropped. Through subsystem tags they
may switch off more rules, each of which is listed in the
[control family reference](control-families.md#what-a-toggle-switches-off-through-tags).

`pam` is both a topic and an umbrella. `linux_compliance_pam_enabled: false` switches off
the rules of the `pam` family and of `pwquality`, `pwhistory` and `faillock`, and the
allow-list entry `linux_compliance_remediate_allow_disruptive: [pam]` allows all four, as
before the split. There is no toggle and no allow-list entry for the rules of the `pam`
family alone: to remediate only those, allow `pam` and switch `pwquality`, `pwhistory` and
`faillock` off with their own toggles.

## Subsystem tags

A rule belongs to one family, often the family of the mechanism it uses, and may carry
subsystem tags: further families whose subsystem the rule is about (FREES-165). The
permissions of `/var/log/sssd` are in `file_permissions` and tagged `sssd`, so
`linux_compliance_sssd_enabled: false` switches them off too. A rule is off when the
toggle of its family, of its family's umbrella, of one of its tags or of a tag's umbrella
is `false`, so `linux_compliance_services_enabled: false` switches off the rules tagged
`sssd` as well. Tags only add ways to switch a rule off: a tag toggle that is `true` never
switches a rule on, and a rule toggle that is set still wins over every topic toggle. Tags
do not change what is disruptive: the allow-list and the disruptive flag stay properties
of the family. Audit rules (`auditd`) are never tagged, because auditing changes to a
subsystem is not configuring it. The tags, how they are derived from the content, and
every rule that a toggle switches off through them are listed in the
[control family reference](control-families.md#subsystem-tags).

## Controlling variable

When a rule is off, `disabled_by` names the first toggle that is `false` in this order:
the umbrella toggle of its family, the family toggle, then for each subsystem tag in
alphabetical order the umbrella toggle of the tag and the tag toggle, else the rule
toggle. So when a rule toggle and its family toggle are both `false`, `disabled_by` names
the family toggle. If the family toggle is later set back to `true`, the rule stays off and
`disabled_by` changes to the rule toggle.

## Rule toggle names and declarations

A rule toggle is `linux_compliance_rule_<rule_short_id>_enabled`, where the short
identifier is the rule identifier without `xccdf_org.ssgproject.content_rule_`, in lower
case, with every character other than a letter, a digit or `_` replaced by `_`. For
example, `kernel_module_usb-storage_disabled` has the toggle
`linux_compliance_rule_kernel_module_usb_storage_disabled_enabled`. The generator fails
if two rules would share a toggle.

Only the topic toggles are role defaults and argument specification options. Rule
toggles are not declared (amendment of FREES-53 to ADR 0011), because declaring more than
a thousand of them slowed every role run down by several seconds per host. A rule toggle
that is not set follows its family toggle, exactly as a declared default would. A rule
toggle that is set is validated by both roles before anything is scanned or changed: it
must belong to a catalogued rule and be a boolean. A value copied into the inventory as
`"{{ linux_compliance_<family>_enabled }}"` resolves the same way in both roles, because
both declare every topic toggle; a template that names a variable that is defined nowhere
fails both roles.

Because rule toggles are not argument specification options, set them as inventory
variables (`group_vars`, `host_vars`), play or task `vars`, `include_role` `vars` or extra
variables (`-e`), never as role parameters (`roles: [{role: ..., <toggle>: false}]` or
`include_role` parameters outside `vars`): the role argument validation rejects an
undeclared role parameter before anything runs. Topic toggles are declared and work as
role parameters too.
